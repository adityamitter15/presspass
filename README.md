# PushupTime

Earn social-media minutes by doing pushups. This package contains the app
scaffolding and the Screen Time blocking/metering core: a main app plus three
Screen Time extensions (DeviceActivity monitor, shield configuration, shield
action), generated from `project.yml` via XcodeGen, plus a CocoaPods
dependency (MediaPipe) for the workout module's pose detector.

## Project setup / regen workflow

The project is generated by XcodeGen and then has CocoaPods dependencies
integrated into it, in that order:

```
xcodegen generate
pod install
```

`xcodegen generate` must run first every time `project.yml` changes —
regenerating `PushupTime.xcodeproj` from scratch — and `pod install` must run
after, since it integrates the Pods target/build settings into whatever
`xcodegen` just wrote. Running them out of order (or running `xcodegen`
after `pod install` without re-running `pod install` again) leaves the
project without the Pods integration.

Once both have run, open/build **`PushupTime.xcworkspace`**, not the
`.xcodeproj` — the workspace is what CocoaPods generates to include both the
app project and the `Pods` project. Build commands:

```
xcodebuild -workspace PushupTime.xcworkspace -scheme PushupTimeDev -destination 'generic/platform=iOS' CODE_SIGNING_ALLOWED=NO build
xcodebuild -workspace PushupTime.xcworkspace -scheme PushupTime -destination 'generic/platform=iOS' CODE_SIGNING_ALLOWED=NO build
```

### CocoaPods dependency

`Podfile` declares `pod 'MediaPipeTasksVision', '0.10.21'` (`use_frameworks!`)
for both the `PushupTime` and `PushupTimeDev` targets — this is Google
MediaPipe's on-device pose-landmark detector, used by
`CameraPoseSession.swift` in place of Apple's Vision framework (see "Workout
module" below for why). The version is pinned exactly: 0.10.33+ has a known
XCFramework linking bug. If 0.10.21 ever fails to resolve or link, 0.10.14 is
the documented fallback.

### Pose model asset

`App/Resources/pose_landmarker_full.task` (9.4 MB) is Google's official
BlazePose Full pose-landmarker model, downloaded from MediaPipe's model
storage
(`https://storage.googleapis.com/mediapipe-models/pose_landmarker/pose_landmarker_full/float16/latest/pose_landmarker_full.task`).
It's declared as a bundled **resource** (not a compiled source) for both app
targets in `project.yml`, so it ships inside the `.app` bundle at
`Bundle.main`'s root — verified present in both built
`PushupTimeDev.app`/`PushupTime.app` bundles produced by the build commands
above.

## What's implemented

- **Project scaffolding** — `project.yml` defines 4 targets (`PushupTime`,
  `PushupTimeMonitor`, `PushupTimeShieldConfig`, `PushupTimeShieldAction`),
  all iOS 16.0+, all carrying the Family Controls and App Group entitlements,
  with the three extensions embedded into the app.
- **Shared ledger** (`Shared/SharedStore.swift`) — App Group–backed
  `UserDefaults` store holding `earnedBalanceMinutes`, `isSessionActive`,
  `sessionStartBalance`, and the persisted `FamilyActivitySelection`.
  `BalanceStore` is a type alias for the same store, used where code reads
  more naturally in terms of "the balance."
- **Shield control** (`Shared/ShieldController.swift`) — wraps a named
  `ManagedSettingsStore` to apply/remove the Screen Time shield for the
  selected apps and categories.
- **Metering core** (`Shared/MeteringCoordinator.swift`, main app only) —
  starts a `DeviceActivity` monitoring session with one threshold event per
  minute of banked balance (capped at 60 events per session; any balance
  above that stays banked for a later session), lifts the shield for the
  session, and stops/re-shields on demand.
- **Monitor extension** (`MonitorExtension/DeviceActivityMonitorExtension.swift`)
  — on each `min_k` threshold, recomputes remaining balance as
  `sessionStartBalance - k` and re-applies the shield once it hits zero;
  re-applies the shield at midnight rollover (`intervalDidEnd`), leaving any
  unused balance for the next day.
- **Shield configuration extension** — dark-themed shield with "Out of
  minutes" / "Do pushups in PushupTime to earn more" / "Earn time", uniform
  across the application, application-category, web-domain, and
  web-domain-category override points.
- **Shield action extension** — primary button closes the shielded app
  (opening another app from a shield action isn't supported by the API);
  secondary button is a no-op.
- **App UI** — `PushupTimeApp` (TabView: Home / Workout / Setup),
  `HomeView` (balance + session controls, refreshes on scene-phase active),
  `SetupView` (Family Controls authorization + `familyActivityPicker`,
  persists selection, "Enable protection" button), and `WorkoutView`, the
  camera/pose pushup-counting module described below.

## Workout module

`App/Workout/` implements the camera/pose pushup-counting module (main app
target only; does not touch `MonitorExtension/`, `ShieldConfigExtension/`,
`ShieldActionExtension/`, or `Shared/MeteringCoordinator.swift`).

- **Camera + pose pipeline** (`CameraPoseSession.swift`) — an
  `AVCaptureSession` on the front camera, delivering frames to a background
  queue where MediaPipe's `PoseLandmarker` (BlazePose Full, running mode
  `.video`) detects a body, converted to a `PoseFrame` (`PoseFrame.swift`):
  timestamp + `[JointName: (x, y, confidence)]`, normalized `[0, 1]` in
  image space, origin bottom-left, y up. `BlazePoseMapping.swift` maps
  BlazePose's 33 landmarks (origin top-left, y down) onto the `JointName`
  subset this app uses (`nose, neck, leftShoulder, rightShoulder,
  leftElbow, rightElbow, leftWrist, rightWrist, leftHip, rightHip, root,
  leftKnee, rightKnee, leftAnkle, rightAnkle`), flipping y to match
  `PoseFrame`'s convention, synthesizing `neck`/`root` as shoulder/hip
  midpoints, and dropping landmarks with visibility below 0.1.
  `CameraPreviewView.swift` wraps the `AVCaptureVideoPreviewLayer` for
  SwiftUI; `SkeletonOverlayView.swift` draws joints/bones over it.
  `NSCameraUsageDescription` is set in `App/Info.plist`. Vision's
  `VNDetectHumanBodyPoseRequest` was replaced with BlazePose because Vision
  reliably lost the body at the bottom of a pushup filmed head-on from floor
  level; this also removed the orientation auto-calibration workaround the
  Vision path needed (BlazePose is fed buffers with a known, fixed
  orientation since the capture connection already applies portrait +
  mirrored).
- **Feature extraction** (`PushupFeatureExtractor.swift`) — a byte-for-byte
  Swift mirror of `training/features.py`'s "v1" contract: per frame, a
  25-dim `[Float]` (or `nil` below the confidence gate). Normalizes by
  translating to the hip-center origin, scaling by torso length, and
  mirroring so the shoulder-center is never left of the hip-center; emits
  10 core joints' normalized (x, y) plus 5 angles (both elbow angles, both
  body-line angles, torso-vs-horizontal). If `features.py` ever changes,
  this file must change identically (see that module's docstring) — a
  model trained on one won't score correctly against the other.
- **Classifier abstraction** (`PoseClassifier.swift`) — `PoseClassifier`
  protocol, `PoseLabel` enum (`up` / `down` / `notPushup`, raw values
  matching `training/dataset.py`'s `VALID_LABELS`). `HeuristicPoseClassifier`
  is the shipped default: mean elbow angle thresholds at 100°/150° for
  down/up, ambiguous middle band continues the previous label at low
  confidence, and torso >35° off horizontal forces `notPushup`.
  `CoreMLPoseClassifier` loads `PushupPoseClassifier.mlmodelc` from the
  bundle via the generic `MLModel` API (not an auto-generated model class,
  so there's no build-time dependency on a model that doesn't exist yet);
  `PoseClassifierFactory.makeDefault()` picks it when present, otherwise
  falls back to the heuristic.
- **Rep counting** (`RepCounter.swift`) — EMA-smooths (alpha 0.3) the
  per-frame label confidence; hysteresis enters a phase at confidence
  ≥0.6 and only exits once the current phase's own confidence has decayed
  to ≤0.4 *and* the other phase has crossed the enter threshold; each
  phase requires a minimum 0.5s dwell before a further transition is
  accepted. A rep counts on every down→up transition. Anti-cheat: frames
  are ignored outright if the torso isn't within ~35° of horizontal or if
  any of the wrists/shoulders/hips are below a confidence floor; a rep
  started less than one second after the previous counted rep is tracked
  as `rejectedReps` rather than counted, so rapid-fire attempts show up in
  the UI instead of silently not incrementing.
- **Workout UI** (`WorkoutView.swift`, `WorkoutViewModel.swift`) — camera
  preview + skeleton overlay, big rep counter, current state label,
  earned-minutes preview (1 rep = 1 minute), a placement hint when no body
  is detected, and Start/Finish buttons. Finish calls
  `SharedStore.credit(minutes: reps)` and shows a summary sheet with
  "Start using your minutes", which calls
  `try? MeteringCoordinator.startEarnedSession()`. The DEBUG-only "Credit 3
  test minutes" button (unchanged behavior from the old stub) lives at the
  bottom of the idle Workout screen alongside a "Data collection mode"
  link, so it's still reachable for manual metering-flow testing.
- **Data-collection mode** (`RecordingView.swift`, DEBUG-only, entire file
  gated behind `#if DEBUG` so it compiles out of Release builds) — records
  a labeled landmark session (label picker: up / down / not_pushup), writes
  it as one JSON file per session to the app's Documents directory, and
  lists saved sessions with a `ShareLink` to export each one. Schema is the
  exact contract `training/dataset.py` reads:
  ```json
  {
    "label": "up",
    "source": "free text",
    "frames": [ { "t": 0.033, "joints": { "leftShoulder": [x, y, c], "...": "..." } } ]
  }
  ```
  `t` is seconds since the recording started (measured on-device with a
  wall clock, independent of the camera session's own internal clock);
  `joints` keys are `JointName.rawValue` strings; a joint is simply omitted
  from a frame if the pose detector didn't detect it that frame, matching
  `training/README.md`'s documented contract. To use it: run the app in
  Xcode (DEBUG configuration) on a physical iPhone, open Workout →
  "Data collection mode", pick a label, hold the pose, Stop recording, then
  either `ShareLink` the file off-device into `training/data/raw/` or
  AirDrop/Files-app it there directly, then follow `training/README.md`
  steps 3-5 (`train.py`, `evaluate.py`, copy the exported `.mlmodel` to
  `App/PushupPoseClassifier.mlmodel`, add it to the Xcode project — once
  present, `PoseClassifierFactory` picks it up automatically).

### Deviations from spec

- The rep-counter's `nextPhase` hysteresis requires the current phase's own
  smoothed confidence to have decayed to the exit threshold (≤0.4) *and*
  the opposing phase to have crossed the enter threshold (≥0.6) before
  transitioning, rather than only checking the opposing phase — this is
  what makes both thresholds actually load-bearing instead of the 0.4 exit
  value going unused.
- `CoreMLPoseClassifier` is built against the generic `MLModel` /
  `MLDictionaryFeatureProvider` API rather than an auto-generated model
  class (the class Xcode would normally generate from a compiled
  `.mlmodelc`), specifically to avoid the target having a compile-time
  dependency on a model file that doesn't exist yet, exactly as required
  by the brief.

## Verified

```
xcodegen generate
pod install
xcodebuild -workspace PushupTime.xcworkspace -scheme PushupTimeDev -destination 'generic/platform=iOS' CODE_SIGNING_ALLOWED=NO build
xcodebuild -workspace PushupTime.xcworkspace -scheme PushupTime -destination 'generic/platform=iOS' CODE_SIGNING_ALLOWED=NO build
```

All four succeed with zero errors, on both the `PushupTimeDev` and
`PushupTime` schemes (pre-existing harmless warnings: a non-exhaustive
switch over `AuthorizationCenter.shared.authorizationStatus` in
`SetupView.swift` covered by `@unknown default`, and an interface-
orientation warning unrelated to the workout module).
`pose_landmarker_full.task` was confirmed present at the root of both built
`.app` bundles under DerivedData's `Build/Products/Debug-iphoneos/`.

## Manual steps left for the owner

1. **Set your signing team** — open `PushupTime.xcworkspace` in Xcode (not
   the `.xcodeproj` — see "Project setup / regen workflow" above) and pick a
   development team for all 4 targets (Signing & Capabilities tab). The
   build above runs with `CODE_SIGNING_ALLOWED=NO` for CI-style verification
   only.
2. **Run on a physical iPhone** — `FamilyControls`/Screen Time APIs
   (authorization, the shield, DeviceActivity monitoring) do not work in the
   Simulator, and the workout module's camera pipeline needs a real camera
   too. You'll also need to enable the Family Controls capability for your
   Apple Developer account/App ID if you haven't already.
3. **Train and ship a model when ready** — the workout module ships with
   only the heuristic classifier; see "Data-collection mode" above for the
   loop that produces `PushupPoseClassifier.mlmodel` and wires it in.
